# STEP 1 — 사업 모델의 논리적 결점과 수익성 위험

기준일 2026-11-18. 숫자는 `config/finance.toml` 의 **가정**과 `services/analytics/finance.py` 산식으로 계산한 값이며 업계 벤치마크가 아니다. 외부 사실은 [API_ACCESS_MATRIX.md](API_ACCESS_MATRIX.md) 의 조사 결과(출처·확인 수준 표기)를 따른다.

## 결론

**지금 가정(1일 1콘텐츠, 노동 기회비용 포함)으로는 연 조정 ROE 25% 가 나오지 않는다.** 기준 시나리오에서 손익분기에 필요한 조회수는 콘텐츠 1개당 약 12만 회(월 360만 회)인데, 가정한 12개월차 콘텐츠당 조회는 1.5만 회다. 8배 차이다. 자동화 시스템을 먼저 크게 만드는 것보다, **구매 동선(조회→클릭)을 얼마나 짧게 만들 수 있는지를 30개 콘텐츠로 먼저 실측**하는 것이 이 사업의 첫 번째 관문이다.

## 1. 숫자로 본 구조적 한계

| 항목 | 값 | 근거 |
|---|---|---|
| 주문 1건당 수수료 | 약 1,950원 (65,000 × 3%) | 사용자 가정. 쿠팡 기본 수수료 3% (가이드, 검색 색인 확인) |
| 월 고정비 | 1,000,000원 (현금 250,000 + 노동 30h × 25,000) | 사용자 가정 |
| 월 손익분기 주문 | 약 513건 (취소 5% 반영 시 약 540건) | 1,000,000 ÷ 1,950 |
| 조회 1,000회당 수익 (기준 퍼널 1% × 30% × 5%) | 277.9원 | `tests/test_finance.py` 검산 |
| 월 손익분기 조회 (기준 퍼널) | 약 360만 회 → 콘텐츠당 약 12만 회 | [ROI_REPORT.md](ROI_REPORT.md) |
| ROE 25% 달성 월 조회 (기준 퍼널) | 약 430만 회 → 콘텐츠당 약 14만 회 | 같은 표 |

시나리오별 연간 조정 ROE: 보수 −259%, 기준 −244%, 낙관 +295% (낙관은 4개월차부터 하루 3개로 확대되는 가정 포함). 결과가 극단적으로 갈리는 이유는 **퍼널 비율 세 개를 곱하기 때문**이다. 랜딩 방문율이 1%→2%, 클릭률이 30%→40%, 구매전환율이 5%→8% 로 각각 조금씩만 바뀌어도 조회당 수익은 4.3배가 된다. 이 세 비율은 아직 아무 근거가 없다 — 그래서 첫 30개 콘텐츠의 목적은 '수익'이 아니라 **이 세 비율의 실측**이다.

노동비를 빼고 현금만 봐도 기준 시나리오는 연 −317만 원이다. 현금 손익분기만 해도 월 약 90만 조회(콘텐츠당 3만 회)가 필요하다.

## 3. 수익성 위험 순위

1. **퍼널 병목 (영향 최대)** — 숏폼 시청자가 프로필까지 오는 비율. 근거 없음. 측정 전에는 어떤 자동화도 돈이 되지 않는다.
2. **노동 기회비용** — 월 75만 원으로 현금비(25만 원)의 3배. 자동화의 경제적 가치는 '콘텐츠를 많이 만드는 것'이 아니라 **월 30시간을 줄이는 것**이다. 운영시간을 실측해 기록할 것.
3. **수수료 단가** — 2만 원대 상품은 주문당 600원 안팎. 쿠팡은 클릭 후 24시간 내 **다른 상품 구매도 인정**하므로 실제 객단가는 상품가보다 클 수 있으나, 확인 전에는 상품가 기준으로 보수 계산(점수 엔진이 그렇게 함).
4. **계정 단위 정책 위험** — 쿠팡 최종 승인 반려(1위 사유: 고지 누락), 플랫폼 원본성·반복 콘텐츠 정책. 한 번 막히면 매출 0.
5. **API 접근 일정** — 네이버 DataLab 기존 키는 2027-06-30 종료, 이후 API HUB(월 5만 회 한도, 검색 색인 확인). 쿠팡 API 는 매출이 생겨야 열림 — 닭과 달걀.

| Instagram 체험 릴스(trial reels) | 비팔로워에게만 먼저 노출 → 후킹 A/B 를 계정 영향 없이 | Graph API `trial_params` 지원(2025-12 changelog) |

## 5. 그래서 이렇게 진행한다

1. **MVP 는 '측정 장치'로 만든다** — 생산 자동화보다 측정(유입경로별 랜딩 방문·클릭, sub_id 귀속)이 먼저. 구현 완료.
2. **첫 30개는 사람이 고르고 사람이 승인한다** — 상품 입력은 수동(사양 직접 확인), 평가·대본·영상·QA 는 자동. `AUTO_PUBLISH=false`.
3. **30개 후 판정 기준** — 실측 랜딩 방문율 × 클릭률 × 전환율로 조회당 수익을 계산하고, [ROI_REPORT.md](ROI_REPORT.md) 손익분기 표에 넣어 필요한 콘텐츠당 조회수를 다시 낸다. 그 조회수가 현재 실측 평균의 3배 이내면 확대 검토, 그 이상이면 채널(YouTube 쇼핑 제휴 등) 전환 검토. 30개는 통계적 확정 표본이 아니라 방향 판단용이다.
4. **실제 상품을 직접 써본 콘텐츠를 일부 섞는 실험** — 실촬영은 신뢰도·원본성 정책 모두에 유리하지만 상품 구매비가 든다(2만 원 상품 = 주문 약 33건분 수수료). 이미 가진 물건부터.

## 6. 자체 검토로 확인한 결함·운영 리스크 (REV02 추가)

코드와 운영 설계를 다시 검토해 확인한 것. 결정이 필요한 것은 [DECISIONS.md](DECISIONS.md), 자동화 관점 정리는 [AUTOMATION_REVIEW.md](AUTOMATION_REVIEW.md).

**코드 결함 (확인)**
1. 크래시 후 `job_runs` 가 `running` 으로 남으면 `--force` 로도 복구 불가 — 재현 확인, 그날 파이프라인 정지. 임시 복구는 [RUNBOOK.md](RUNBOOK.md).
2. 관리자 '실행' 버튼·`/api/jobs/run` 이 단계를 웹 요청 안에서 동기 실행 → gunicorn 기본 30초 시간초과에 영상 제작(약 75초)이 걸림 → 1번 유발.
3. 쿠팡 API 모드로 바꾸면 후보 전부 '보류'(응답에 사양 없음, 이미지는 표시 전용 권리) → 매일 '평가 통과 0개'로 멈춤. 사양 확인 대기열이 필요.
4. 쿠팡 검색을 키워드마다 호출 — 시간당 10회 제한(커뮤니티 정보, 미확인)이면 초과.
5. 초기 실운영 경로인 수동 상품 입력이 JSON 편집뿐(등록 화면 없음).
6. 메인 → 상품 이동 시 `src` 유실 → 인스타 유입이 'direct'로 집계.
7. 관리자 로그인 시도 제한 없음, `SCF_ENV=dev` 공개 배포 시 고정 개발용 SECRET_KEY, 프록시 뒤 이벤트 요청 제한이 공용 버킷.

**기능은 있으나 약한 부분**: A/B 는 B 를 만들기만 하고 게시 안 함 · 실상품 영상은 그라디언트 배경 슬라이드(템플릿 반복 정책 위험) · 무음 · 규칙 기반 구매심리는 사람 메모 재배열 · 재검증은 판매처 재조회 아님 · 사실 검사는 숫자 없는 과장을 못 잡음 · 외부 API 실호출 0건(가짜 응답 테스트만), Docker 미빌드 · 백업 없음.

**측정·사업**: 30개로는 구매전환율 판정 불가(콘텐츠당 1,000조회 가정 시 주문 약 4.5건) · sub_id 별 실적 분리 미확인 → 대부분 미귀속, 학습 보정은 몇 달간 사실상 미작동 · 사람 확정 6곳의 노동이 월 30시간 가정을 넘을 가능성 · 점수 가중치는 판단값.
